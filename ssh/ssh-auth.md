## 1. Что такое SSH-ключи и зачем они нужны

SSH-аутентификация построена на асимметричной криптографии: есть пара ключей — **приватный** (остаётся только у владельца) и **публичный** (раздаётся серверам/сервисам). Сервер, зная твой публичный ключ, может проверить, что у владельца есть соответствующий приватный, — без передачи пароля по сети.

Преимущества перед паролем:

- устойчивость к перебору (брутфорсу);
- можно полностью отключить парольный вход;
- один и тот же механизм работает и для входа на сервер, и для Git, и для туннелей — везде, где используется протокол SSH.

### Типы ключей

| Тип              | Когда использовать                                                   |
| ---------------- | -------------------------------------------------------------------- |
| `ed25519`        | **По умолчанию для всего нового.** Короче, быстрее и безопаснее RSA. |
| `rsa` (4096 бит) | Только если целевая система старая и не умеет `ed25519`.             |
| `ecdsa`          | Обычно избегать (вопросы к выбору кривых NIST).                      |

### Генерация ключа

```bash
# -t ed25519 — тип ключа
# -C "comment" — комментарий (обычно почта или назначение ключа)
# -f путь — куда сохранить (если не указано — спросит; по умолчанию ~/.ssh/id_ed25519)
ssh-keygen -t ed25519 -C "comment" -f ~/.ssh/id_ed25519
```

Флаг `-f` важен, если ключей будет несколько: без него `ssh-keygen` попытается использовать имя по умолчанию и либо спросит, либо перезапишет существующий файл.

Passphrase (кодовая фраза) — дополнительное шифрование приватного ключа на диске. Если файл ключа украдут, без passphrase он бесполезен для злоумышленника. Можно оставить пустым (`Enter`) — тогда ключ работает без дополнительного ввода пароля при каждом использовании, но и не защищён при краже файла.

### Прочие операции с ключами

```bash
# Достать публичный ключ из приватного, если id_ed25519.pub потерялся
ssh-keygen -y -f ~/.ssh/id_ed25519 > ~/.ssh/id_ed25519.pub

# Сменить passphrase у существующего ключа
ssh-keygen -p -f ~/.ssh/id_ed25519

# Посмотреть fingerprint ключа
ssh-keygen -lf ~/.ssh/id_ed25519.pub
```

## 2. Структура `~/.ssh` и права доступа

SSH **молча отказывается** использовать файл, если права на него слишком открытые — это не баг, а защита от чтения секретов другими пользователями системы.

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
```

Папка `~/.ssh/` есть на любой машине, участвующей в SSH, но **набор файлов внутри зависит от роли** этой машины — клиент она или сервер (одна и та же машина может быть и тем, и другим одновременно, но это две разные роли с разными файлами).

### На клиенте

| Файл / папка                      | Назначение                                        | Права числовые    | Права символьные                |
| --------------------------------- | ------------------------------------------------- | ----------------- | ------------------------------- |
| `~/.ssh/`                         | сама папка                                        | `700`             | `drwx------`                    |
| `id_ed25519` (приватный ключ)     | секрет, никому не передавать                      | `600`             | `-rw-------`                    |
| `id_ed25519.pub` (публичный ключ) | отсюда копируется на серверы                      | `644`             | `-rw-r--r--`                    |
| `config`                          | настройки *твоих исходящих* подключений           | `600`             | `-rw-------`                    |
| `known_hosts`                     | отпечатки серверов, к которым *ты* подключался    | `600` (или `644`) | `-rw-------` (или `-rw-r--r--`) |
| `known_hosts.old`                 | автоматический бэкап `known_hosts` (см. раздел 4) | `600`             | `-rw-------`                    |

### На сервере

| Файл / папка      | Назначение                                                                                    | Права числовые | Права символьные |
| ----------------- | --------------------------------------------------------------------------------------------- | -------------- | ---------------- |
| `~/.ssh/`         | сама папка                                                                                    | `700`          | `drwx------`     |
| `authorized_keys` | список чужих публичных ключей, которым разрешён вход **на эту машину под этим пользователем** | `600`          | `-rw-------`     |

`authorized_keys` появляется только там, где машина **принимает** SSH-подключения. На обычном клиенте этого файла в норме нет вообще, т.к. он **НЕ принимает** SSH-подключения.

Проверка после настройки:

```bash
ls -la ~/.ssh/
```

### Копирование публичного ключа на сервер

Есть два равнозначных способа — автоматический и ручной.

```bash
# Автоматически: сама создаст ~/.ssh, добавит ключ и выставит правильные права
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server_ip

# Вручную — то же самое действие одной строкой, если ssh-copy-id недоступна
cat ~/.ssh/id_ed25519.pub | ssh user@server_ip "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys"
```

Обе команды на сервере в итоге просто дописывают содержимое копируемого `.pub`-файла новой строкой в конец `~/.ssh/authorized_keys`.

### Формат `authorized_keys`

Формат — один публичный ключ на строку. Можно добавить сколько угодно ключей (например, с разных устройств или для разных админов) — каждый новый просто дописывается отдельной строкой в конец файла:

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGVy... laptop-key
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIHjk... phone-key
```

Ключ можно ограничить префиксом прямо в той же строке — полезно для «служебных» ключей (например, CI/CD или deploy-ключ, которому не нужен полноценный шелл):

```text
command="/usr/bin/git-shell",no-port-forwarding,no-X11-forwarding,no-agent-forwarding ssh-ed25519 AAAA... deploy-key
```

## 3. Алиас в `config`

Файл [`~/.ssh/config`](config) (кодировка UTF-8 **без BOM**, права `600`) позволяет не писать длинные команды подключения и хранить настройки per-хост.

Правило: блоки читаются по порядку сверху вниз, для каждого параметра используется **первое** совпавшее значение — поэтому более специфичные `Host` пишут выше общих/`Host *`.

Ключевые директивы:

| Директива                | Что делает                                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `HostName`               | реальный адрес/домен сервера                                                                                                                                 |
| `User`                   | имя пользователя для входа                                                                                                                                   |
| `Port`                   | порт (если не 22)                                                                                                                                            |
| `IdentityFile`           | путь к приватному ключу для этого хоста                                                                                                                      |
| `IdentitiesOnly yes`     | использовать **только** указанный ключ, не перебирать все ключи из agent'а. Без этого при нескольких ключах легко словить `Too many authentication failures` |
| `ServerAliveInterval 60` | keep-alive: интервал (сек) между служебными пакетами, которые не дают роутеру/провайдеру считать долгую бездействующую сессию мёртвой                        |
| `ServerAliveCountMax 3`  | сколько таких пакетов подряд могут остаться без ответа, прежде чем SSH сам разорвёт сессию как мёртвую                                                       |

`ServerAliveInterval` и `ServerAliveCountMax` решают проблему зависших сессий терминалов при неактивности в ней.

Реже нужные директивы — не для базового сценария «один клиент → один VPS», но полезно знать, что они существуют:

- `ProxyJump host2` — зайти на сервер через промежуточный (bastion) хост;
- `ForwardAgent yes` — пробросить свой ssh-agent на удалённый сервер (осторожно: пока сессия жива, им может воспользоваться и удалённая машина);
- `AddKeysToAgent yes` — добавлять ключ в agent автоматически, без ручного `ssh-add`;

## 4. `known_hosts` и `known_hosts.old`

`known_hosts` хранит отпечатки (fingerprints) серверов, к которым уже осуществлялось подключение — это защита от MITM-атак. Если отпечаток сервера вдруг изменился, SSH предупредит об этом до ввода каких-либо данных.

При первом подключении к новому серверу:

```text
Are you sure you want to continue connecting (yes/no)?
```

`yes` → отпечаток сохраняется в `known_hosts`.

Если сервер переустанавливали, меняли на нём ssh-ключи хоста, или IP-адрес переиспользовали, например, у VPS-провайдера, то при следующем подключении появится жёсткое предупреждение:

```text
REMOTE HOST IDENTIFICATION HAS CHANGED!
```

**Не игнорировать бездумно.** Сначала убедиться, что изменение ожидаемо (сам переустановил сервер / провайдер это подтверждает), и только потом убрать устаревшую запись:

```bash
ssh-keygen -R hostname_или_ip
```

Именно эта команда перед удалением записи автоматически создаёт бэкап старого файла — отсюда и берётся `known_hosts.old`. Если предупреждение неожиданное — это повод разбираться, а не сразу чистить `known_hosts`.
