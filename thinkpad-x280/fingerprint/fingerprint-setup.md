# Отпечаток пальца

На большинстве ноутбуков Lenovo X280 используется `Synaptics` (или иногда `Validity`), который часто требует дополнительной настройки в Linux.

## Шаг 1: Проверка совместимости

1. Узнать точную модель сканера:

    ```bash
    lsusb
    ```

    Найти строку, содержащую слова `Fingerprint`, `Synaptics`, `Validity` или `06cb` (часто это код `Synaptics`). Пример вывода: `ID 06cb:009a Synaptics, Inc. Metallica MIS Touch Fingerprint Reader`

2. Свериться с базой совместимости `libfprint`:

    Перейти на официальную страницу поддерживаемых устройств проекта [libfprint](https://fprint.freedesktop.org/supported-devices.html).
   * Если устройство там есть — нужно разбираться, почему не подхватилось.
   * Если устройства нет — скорее всего оно работать не будет с этим драйвером.

## ~~Шаг 2:~~ `fprintd` (не работает на этом железе)

Это стандартный стек для отпечатков в Linux, но на X280 с чипом `06cb:009a` он не определяет сканер даже после установки. Сразу перейти к **шагу 3**.

1. Установка необходимых пакетов:

    ```bash
    sudo apt update
    sudo apt install fprintd libpam-fprintd
    ```

   * `fprintd` — это демон (служба) для работы с отпечатками;
   * `libpam-fprintd` — модуль, который позволяет использовать отпечаток для входа в систему (PAM — это механизм аутентификации).

2. Проверить, видит ли система сканер:

    ```bash
    fprintd-list
    ```

    Если система выведет что-то вроде `Found a device`, значит, повезло — драйвер подошел.

3. Записать отпечаток пальца:

    ```bash
    fprintd-enroll
    ```

   * Система попросит приложить палец несколько раз. По умолчанию записывается палец, который использовался первым (обычно правый указательный).
   * Если несколько пользователей, или есть необходимость записать палец для конкретного пользователя:

    ```bash
    fprintd-enroll -f "ЛЕВЫЙ_УКАЗАТЕЛЬНЫЙ" имя_пользователя
    ```

4. Настройка входа в систему:
   * После установки `libpam-fprintd`, система должна автоматически добавить отпечаток как опцию входа;
   * Теперь при попытке войти в систему, запуске команд через `sudo` или разблокировке экрана, система попросит либо пароль, либо прикосновение пальца.

5. Проверка и управление:
   * Просмотр сохраненных отпечатков: `fprintd-list имя_пользователя`
   * Удаление всех отпечатков: `fprintd-delete имя_пользователя`

## Шаг 3: `python-validity` (рабочий вариант)

Если стандартный `fprintd` не видит сканер, возможно, эта модель, которая требует проприетарного драйвера или работает через `libfprint` из нового репозитория.

Можно попробовать установить более свежую версию `libfprint` из проекта FPC (часто используется в новых Lenovo).

Процесс состоит из нескольких этапов: удаление стандартного пакета, подключение специального репозитория, установка драйвера и, возможно, сброс настроек чипа.

1. Удалить стандартный пакет `fprintd`, если он был установлен ранее. Это нужно для избежания конфликтов.

    ```bash
    sudo apt remove fprintd
    ```

2. Добавить PPA (Personal Package Archive) `uunicorn/open-fprintd`. Именно здесь находятся собранные пакеты `python-validity` и `open-fprintd`.

    ```bash
    sudo add-apt-repository ppa:uunicorn/open-fprintd
    sudo sed -i 's/resolute/noble/' /etc/apt/sources.list.d/uunicorn-ubuntu-open-fprintd-resolute.sources
    ```

    Launchpad собирает пакеты PPA отдельно под каждый релиз Ubuntu (jammy, noble, resolute и т.д.) — это разные build-окружения. Мейнтейнер `uunicorn/open-fprintd` ещё не выполнил сборку под Resolute (26.04), поэтому там физически нет Release-файла, хотя сам PPA существует и работает для старых релизов. Пакеты там в основном на Python/udev и от конкретной версии Ubuntu не зависят, поэтому можно смело подставить suite от старого релиза (noble) — apt возьмёт готовые бинарники оттуда.

    * 22.04 LTS — Jammy (Jellyfish);
    * 24.04 LTS — Noble (Numbat);
    * 26.04 LTS — Resolute (Raccoon).

3. Обновить список пакетов и установить необходимые компоненты:

    ```bash
    sudo apt update
    sudo apt install open-fprintd fprintd-clients python3-validity
    ```

   * `open-fprintd` — это форк `fprintd`, работающий в связке с `python-validity`;
   * `fprintd-clients` — утилиты для управления (например, `fprintd-enroll`);
   * `python3-validity` — сам драйвер.

4. Попробовать записать отпечаток стандартной командой:

    ```bash
    fprintd-enroll
    ```

    Если команда выполнится успешно и попросит приложить палец — всё работает! Переход к шагу 6.

5. Если возникла ошибка (например, `list_devices failed:`) — это нормально для первого запуска. Часто требуется выполнить сброс (factory reset) чипа, как описано в разделе "Error situations" репозитория. Необходимо выполнить следующие команды по порядку:

    ```bash
    # Остановка сервиса, если он запущен
    sudo systemctl stop python3-validity

    # Сброс прошивки сенсора (важно!)
    sudo validity-sensors-firmware

    # Выполнение полного сброса чипа до заводских настроек
    sudo python3 /usr/share/python-validity/playground/factory-reset.py

    # Запуск сервиса заново
    sudo systemctl start python3-validity

    # Новая попытка записать отпечаток
    fprintd-enroll
    ```

    Если какая-то из команд пожалуется на "device busy", значит, сервис `python3-validity` не до конца остановился. Необходимо повторить `sudo systemctl stop python3-validity` и попробовать снова.

6. Чтобы включить аутентификацию по отпечатку для входа в систему после успешной записи отпечатка, нужно разрешить системе использовать его:

    ```bash
    sudo pam-auth-update
    ```

    В открывшемся псевдографическом меню с помощью пробела необходимо отметить галочкой пункт `Fingerprint authentication` (или похожий). С помощью Tab перейти на `Ok` и нажать `Enter`.

7. Проверить, что это же автоматически накрыло `sudo` в терминале — обычно `/etc/pam.d/sudo` уже подключает `common-auth`, который правит `pam-auth-update`:

    ```bash
    grep common-auth /etc/pam.d/sudo
    ```

    Если строка найдена — отдельно настраивать `sudo` не нужно, пароль при `sudo` в терминале тоже можно будет заменить отпечатком.

8. Перезагрузить систему, чтобы изменения гарантированно вступили в силу.

    ```bash
    sudo reboot
    ```

## Проблема: не работает после сна/гибернации

Как указано в инструкции, нужно включить специальные сервисы:

```bash
sudo systemctl enable open-fprintd-resume open-fprintd-suspend
```

Даже с включенными сервисами, датчик отпечатков пальцев (особенно на ноутбуках с сенсорами `Synaptics`, которые используют `python3-validity`) часто "засыпает" слишком глубоко и корректно не просыпается.

### Вариант 1. Использовать системные хуки сна/пробуждения (рабочий вариант)

Логика исправления сканера выносится в **системный сервис (systemd unit)**, который запускается после выхода из сна.

[fingerprint-resume.sh](fingerprint-resume.sh) - `/usr/lib/systemd/system-sleep/fingerprint-resume.sh`

Сделать скрипт исполняемым:

```bash
sudo chmod +x /usr/lib/systemd/system-sleep/fingerprint-resume.sh
```

Чтобы убедиться, что скрипт отработал можно посмотреть лог с помощью следующей команды:

```bash
journalctl | grep "fingerprint: fixed after"
```

### ~~Вариант 2.~~ Создание собственного правила пробуждения (не рабочий вариант)

Сервисы `open-fprintd-resume` часто срабатывают слишком рано, когда устройство еще не готово. Можно создать правило `udev`, которое будет перезапускать сервис при пробуждении системы.

1. Файл с правилами:

    [99-fingerprint-resume.rules](99-fingerprint-resume.rules) - `/etc/udev/rules.d/99-fingerprint-resume.rules`

    **Важно:** узнать `idVendor` и `idProduct` можно с помощью команды `lsusb`  
    **Вывод команды**: `Bus 001 Device 008: ID 06cb:009a Synaptics, Inc.`  
    Вот эти значения `06cb:009a` и нужно подставить в правило выше (после `idVendor` и `idProduct`).

2. Перезагрузка и применение правил `udev`

    ```bash
    sudo udevadm control --reload-rules
    sudo udevadm trigger
    ```

❗ При использовании этого варианта возникает **проблема** долгой загрузки системы ~2 мин. Причина не в том, что правило «просто долгое» — дело в самом способе вызова. `RUN+=` в udev выполняется внутри udev-воркера, который работает в урезанном окружении и не должен запускать долгие или блокирующие команды. `systemctl restart` ждёт ответа от systemd-менеджера, а тот в этот момент может ждать завершения обработки очереди udev (`systemd-udev-settle`) — получается циклическое ожидание. Поэтому зависание длится ровно до таймаута `systemd-udev-settle.service` (120 секунд), а не просто «потому что команда долгая».
